# 如何参考开源后端项目（学习路径）

> 目的：学会「读架构」，而不是「抄目录」。读 3 个项目、每个只追一个用例，胜过克隆 10 个模板。

## 1. 要不要参考？要，但有前提

参考开源项目是练架构直觉最有效的方式之一，但参考的方式决定你是「学会」还是「被带偏」：

- ✅ 参考：目录分层思路、依赖方向、事务所有权、错误处理、状态机写法。
- ❌ 照抄：库选型、文件夹命名、微服务拆分（这些要服务于你自己的业务和规模）。

判断标准：**你读完能不能回答「为什么它这么分层」**。答不出来，说明还没读进去。

## 2. 三种主流架构，先认清它们在说什么

| 架构 | 一句话 | 和我们的关系 |
| --- | --- | --- |
| 分层架构（Layered） | Handler → Service → Repository，一层调一层 | 我们的起点 |
| 干净架构（Clean） | 业务核心在最内层，依赖只朝内，不朝外 | 我们的 domain 接口 + infrastructure 适配器 |
| 六边形/端口适配器（Hexagonal） | 应用是六边形核心，HTTP/DB 都是插到端口上的适配器 | 和干净架构本质同一套思想 |
| DDD 模块化单体 | 按业务模块（订单/支付/营销）拆包，模块内再分层 | 我们 LTerm 蓝图里的 core/domain/order.go + app/server/service/order_svc.go 就是它的简化版 |

关键认知：**贫血 DDD 不是新架构，而是「干净架构 + DDD 的模块划分 + 贫血实体」的组合**。所以你看懂干净架构，就看懂了一大半。

## 3. 推荐参考项目（选 2~3 个即可）

### 3.1 golang-standards/project-layout

- 地址：https://github.com/golang-standards/project-layout
- 学什么：Go 目录约定 —— `cmd/`、`internal/`、`pkg/` 各放什么；为什么业务代码要放 `internal/`。
- 注意：它只是「布局约定」，不是架构；不要以为照着建目录就学会了。

### 3.2 evrone/go-clean-template

- 地址：https://github.com/evrone/go-clean-template
- 学什么：干净架构的标准分层；业务逻辑与框架解耦；依赖注入怎么手动组装；一个用例（usecase）怎么组织。
- 注意：它是模板，结构偏「通用」；读它的 `usecase` 和 `internal/entity` 即可，别照搬它的包命名。

### 3.3 bxcodec/golang-ddd-modular-monolith-with-hexagonal

- 地址：https://github.com/bxcodec/golang-ddd-modular-monolith-with-hexagonal
- 学什么：**最接近我们的目标** —— 模块化单体 + 六边形架构；一个业务模块内部如何拆 domain/application/interface；仓储接口（端口）和 PostgreSQL 实现（适配器）怎么分离。
- 注意：它包含较多 DDD 概念（值对象、领域事件），先看模块结构和一个用例，不要一次读全部。

## 4. 五步阅读法（每个项目都这么做）

1. **先看 README 和目录树**：找出「业务代码」和「基础设施代码」分别在哪。
2. **选一个垂直用例**：比如订单支付。从头到尾追一遍：
   `HTTP handler → 用例方法 → 实体/状态判断 → 仓储接口 → PostgreSQL 实现`
3. **回答 5 个问题**：
   - 依赖方向是从外到内还是乱的？
   - 事务在哪里开启？仓储能不能自己开事务？
   - 状态/业务规则写在哪个层？
   - 错误是怎么从业务层传到 HTTP 层的？
   - 如果我要加一个「退款」用例，要动哪几个文件？
4. **对照自己的文档**：拿 [项目架构-贫血DDD.md](项目架构-贫血DDD.md) 逐项对比，差异记录下来。
5. **写一页分析**：用你自己的话讲「这个项目处理一次支付回调，数据是怎么流转的」。讲不清楚就是没读懂。

## 5. 练习：给你的第一个任务

去 bxcodec 的项目里找一个业务模块（订单/支付/库存任一），只读它，然后回答：

1. 它的 handler 到 repository 一共经过几层？每层一句话职责。
2. 它有没有「一个用例一个事务」？事务在哪里开？
3. 状态迁移（比如支付成功）写在实体里还是用例里？
4. 换成我们的 LTerm，哪个设计你会直接抄、哪个你会改？为什么？

写完发我 review，我会先追问「为什么」，再帮你补边界。

## 6. 参考时的三个坑

| 坑 | 表现 | 对策 |
| --- | --- | --- |
| 模板依赖过重 | 项目变成「脚手架 + 空代码」 | 只参考，不克隆；自己从零建 |
| 过度工程 | 一个 CRUD 项目塞 CQRS + 事件溯源 | 先看清它解决什么问题，你的规模是否需要 |
| 库选型被带偏 | 跟着模板用 GORM/MongoDB | 结合你的技术栈（Gin + PostgreSQL + pgx/sqlx） |

## 7. 小结

参考开源项目的正确姿势：**选一个用例，追一条数据流，回答五个问题，写一页分析**。

看完 2~3 个项目，你会发现所有「好架构」都在重复同一件事：业务核心向内、依赖方向向下、事务只有一个入口。这就是你接下来要练的直觉。
