# 01 管理员模块设计（v0.2）

## 1. 范围

系统采用 SaaS 权限边界：平台超级管理员维护全局影片与平台内容，影院管理员维护绑定影院的影厅、座位和场次，并查看本影院经营数据，财务账号只读票房数据。

## 2. 数据模型（复用 + 新增）

复用已有表：`movies`、`cinemas`、`halls`、`seats`、`show_sessions`。
新增表（migrations002）：`admins`、`roles`、`operation_logs`。

| 表 | 用途 | 关键字段 |
| --- | --- | --- |
| admins | 管理员 | username、password_hash、role_id、status |
| roles | RBAC | code(SUPER_ADMIN/CINEMA_ADMIN/FINANCE)、permissions_json |
| operation_logs | 审计 | admin_id、action、target_type/id、detail_json、ip |

`admins` 增加 `cinema_id`（可空）：SUPER_ADMIN 与全局 FINANCE 为空，CINEMA_ADMIN 必须绑定一个影院，绑定影院的 FINANCE 按该影院过滤。影院范围由服务端从当前管理员记录取得，不信任请求参数或 JWT 中的影院值。

鉴权：用户端与管理端使用不同登录入口和同一签名 JWT；请求中间件先校验签名与有效期，再从数据库确认账号状态、角色状态和影院范围。前端守卫只负责隐藏菜单与页面跳转，后端中间件和服务层校验才是最终边界。

### 2.1 SaaS 权限矩阵

| 角色 | 租户范围 | 可以做什么 | 明确不能做什么 |
| --- | --- | --- | --- |
| SUPER_ADMIN | 全平台、全部影院 | 影片 CRUD、平台内容、管理员账号、任意影院运营、全局大盘、票房重建 | 无业务范围限制，但所有关键操作留审计 |
| CINEMA_ADMIN | `admins.cinema_id` 对应影院 | 本影院影厅/座位布局、排期、改价、取消场次、票券核销、本影院大盘；读取影片供排片 | 不能改影片、Banner、优惠券、管理员账号，不能访问其他影院 |
| FINANCE | 全局或绑定影院 | 只读票房大盘 | 不能改价、排期、影厅、影片或账号 |
| USER | 用户自身 | 搜索、选座、下单、支付、退款、改签、积分 | 不能访问任何管理接口 |

> 管理接口统一挂 `AuthAdmin(roles...)` 中间件。涉及影院实体的服务层再次执行角色和 `cinema_id` 校验，避免绕过 HTTP 路由后扩大权限。

## 4. 关键规则

### 4.1 影片

- 下架不影响已开场次；有关联未开场次的影片禁止物理删除（软删除）。

### 4.2 影厅与座位

- `halls.seat_layout_json` 是前端渲染坐标（排/列/类型/不可用位）。
- `seats` 表是售票事实（可售座位），保存影厅时按 layout **diff 同步**：新增/禁用/恢复，不做全量重建（保留座位 ID 稳定，订单历史不断）。

### 4.3 场次排期

- 同一影厅时间不可重叠：应用层校验 + 数据库排他约束（`EXCLUDE USING gist (hall_id WITH =, tstzrange(start_time,end_time) WITH &&)`，需 btree_gist 扩展；课程降级方案：应用层查冲突 + 事务重试）。
- 开场前 30 分钟锁定场次：不可改价/取消（可配置）。
- 取消场次：同一事务释放全部 LOCKED 锁、关闭待支付订单（EXPIRED）。

### 4.4 票价

- `base_price_cents` 基础价 + `price_rules_json` 按座位类型覆盖（如 {"VIP":16000}）。
- 改价影响新订单；已创建订单金额快照不动。

## 5. 审计

改价、发券、取消场次、调账、影片上下架、影厅布局、排期、核销、管理员创建等动作写 `operation_logs`（变更前后 JSON）。审计日志不可由业务接口删除。

## 6. 验收标准

- Given 同影厅重叠时间，When 保存场次，Then 拒绝并提示冲突。
- Given 已开场次，When 改价，Then 拒绝（409）。
- Given 取消场次，When 完成，Then 座位锁全部释放、待支付订单转 EXPIRED。
- Given 管理员改价，When 完成，Then operation_logs 有完整前后值。
